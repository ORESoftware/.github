# TJSV language/runtime boundary integrity

Linear: `DEN-3959`

Primary implementation: `ORESoftware/typespec-json-schema-validator`

Related Lambda rollout: `docs/lambda-oci-tjsv-rollout.md`

This document records the public-safe integrity boundary for TJSV-generated language/runtime evidence. It supplements the Lambda OCI/TJSV rollout and the general dual-authority program; it does not create a third contract authority.

## Authority invariant

TypeSpec and independently authored JSON Schema/OpenAPI remain peer top-level authorities. Neither lane may be generated from the other and then promoted as authoritative.

The following remain downstream evidence only:

- TypeSpec-generated JSON Schema or OpenAPI witnesses;
- Contract IR;
- parity/admission receipts;
- runtime adapters and generated clients;
- language/runtime evidence envelopes;
- source revisions, hashes, and artifact digests.

An unexplained mismatch stops promotion. No generated object or older passing receipt wins by fallback.

`ORESoftware/typespec-json-schema-validator#85` extends that profile with a bounded adversarial regression wave:

- negative cases include unknown operation, unknown provider, missing required request ID, wrong schema version, and extra properties;
- Rust/native, TypeScript/Node, and Dart/Flutter remain simultaneous required language/runtime witnesses;
- adversarial evidence mutations cover schema identity, pass status, runtime identity, source revision, artifact digest, toolchain identity, generator identity, ingress result, egress result, parity receipt binding, and Contract IR binding;
- invalid runtime evidence must stop evaluation and must not be counted as admitted evidence.

The PR is a tests/docs expansion. It intentionally does not broaden the verifier API while documenting the stronger integrity gates below.

## Integrity gap 1: self-digest and receipt-body binding

Tracked by `ORESoftware/.github#174`.

The final language-boundary admission path must independently prove that the supplied Contract IR and retained parity receipt bodies still match the identifiers they carry. Digest-shaped strings are not sufficient by themselves.

Required behavior:

1. reuse canonical TJSV Contract IR verification semantics;
2. recompute the Contract IR `irId` from the canonical body without `irId`;
3. bind the Contract IR admission receipt to the exact supplied parity report by canonical digest as well as exact `runId`;
4. fail closed on stale or tampered bodies;
5. preserve deterministic rule IDs and public Draft 2020-12 receipt contracts;
6. retain TypeSpec/JSON Schema peer authority with generated evidence remaining non-editable.

Negative controls include a mutated declaration with a retained old `irId`, mutated authority metadata, a changed parity report with stale retained digest, missing digest, and a fully current positive control.

## Integrity gap 2: exact current artifact bytes

Tracked by `ORESoftware/.github#175`.

A well-formed evidence envelope must not be able to authorize stale or substituted generated bytes merely because its `artifactDigest`, `sourceRevision`, parity receipt ID, and Contract IR ID are syntactically valid.

Required behavior:

1. provide a containment-safe current-files/current-bytes admission path, or accept a trusted expected digest map produced from those exact inputs;
2. SHA-256 the exact current artifact bytes and compare them with each evidence `artifactDigest`;
3. compare `sourceRevision` with the exact expected immutable commit, not only a 40-hex pattern;
4. reject missing files, path traversal, absolute paths, symlink escape, duplicate aliases, and ambiguous path normalization;
5. bind one evidence envelope to one exact language/runtime target and artifact;
6. emit deterministic evidence without copying source contents, secrets, or private paths into receipts.

Negative controls include post-evidence artifact modification, cross-runtime evidence replay, stale source revision, missing files, traversal/symlink escape, and mixed-current/stale Rust/TypeScript/Dart artifacts.

## Relationship to existing work

These integrity tasks do not replace:

- `#75` — release-channel and compatibility policy;
- `#77` — one repository-local TJSV consumer lock and pin-drift gate;
- `#40` — build/executable provenance;
- `#167` — post-hoc quarantine/revocation after validator or toolchain defects;
- `#168` — bounded Lambda consumer promotion tranches.

The layers are cumulative. A consumer is promotable only when the applicable authority-convergence, current-input integrity, pin/compatibility, runtime evidence, and exact-head CI gates all pass at the same reviewed revision.

## Promotion sequence

1. Run TJSV over independently authored TypeSpec and JSON Schema/OpenAPI authorities.
2. Retain the exact parity receipt and create a content-addressed, non-editable Contract IR.
3. Verify Contract IR self-digest and exact retained parity receipt body.
4. Generate the language/runtime artifacts for the exact source revision.
5. Execute native ingress/egress conformance for each required runtime.
6. Verify each evidence digest against the exact current artifact bytes and exact source revision.
7. Emit the deterministic language-boundary admission receipt.
8. Apply repository-local consumer-lock, compatibility, and release policy.
9. Promote only with exact-head CI evidence; then roll consumers in bounded tranches.

A local test result, mutable branch reference, generated witness, copied evidence envelope, or historical green receipt is not sufficient promotion evidence.
